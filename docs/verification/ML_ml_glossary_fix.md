# Правка идентификаторов: воркер разметки (ML)

Для: Ершов Дарий Кириллович. Файл, который нужно исправить: `src/individual/MLDiagramsCode/ml_l3.puml`.
Этот документ можно целиком отдать нейросети вместе с файлом — в нём есть всё, что нужно для правки.

Причина: при сборке общих диаграмм ЛР № 4 тимлид сверил все `.puml` с глоссарием
`docs/glossary/components.csv`. Диаграмма компонентов воркера разметки — единственная, где
идентификаторы компонентов записаны без префикса контейнера. Из-за этого связь по ID между
диаграммами не строится, и в ЛР № 5 такой файл не пройдёт проверку глоссария в CI.

Содержание диаграммы правильное: состав компонентов, их названия и технологии совпадают с
глоссарием. Менять логику воркера не нужно — только идентификаторы и оформление связей.

## 3. Остальные правки в том же файле

### 3.1 Подключение библиотеки

Было `!include <C4/C4_Component>` — это локальная библиотека PlantUML. Все остальные файлы команды
подключают C4-PlantUML по адресу, и сборка в ЛР № 5 рассчитана на него. Заменить на:

```text
!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/C4_Component.puml
```

### 3.2 Описания контейнеров

У контейнеров пропущен четвёртый аргумент — описание. По правилу команды названия, технологии и
описания берутся из общей диаграммы дословно. Заменить три строки на эти:

```text
Container(message_broker, "Брокер сообщений", "RabbitMQ", "Очереди reviews.labeling (задачи разметки) и cases.events (события по обращениям)")
ContainerDb(database, "База данных", "PostgreSQL 16", "Отзывы, разметка, обращения, история статусов, справочники, витрины аналитики")
```

Границу контейнера записать без технологии в скобках, технология относится к элементу, а не к границе:

```text
Container_Boundary(labeling_worker, "Воркер разметки") {
```

### 3.3 Направление стрелки к брокеру

Сейчас стоит `Rel(message_broker, lw_task_consumer, ...)` — стрелка идёт от брокера к воркеру. Это
противоречит общей диаграмме контейнеров, где связь записана как
`Rel(labeling_worker, message_broker, "Забирает задачи разметки из очереди reviews.labeling", "AMQP")`,
и правилу «стрелка направлена от инициатора сетевого соединения»: подписчик сам открывает соединение
с RabbitMQ и забирает сообщение. Развернуть стрелку.

### 3.4 Протоколы

У каждой связи должны быть описание действия и технический протокол.

| Вид связи | Как сейчас | Как нужно |
|---|---|---|
| Между компонентами внутри воркера | протокол не указан | `"Python Call"` |
| К базе данных | `"SQL"` | `"SQL / TCP"` |
| К брокеру | `"AMQP"` | `"AMQP"` — менять не нужно |

### 3.5 Описания связей

Подписи вида `"2. id отзыва"` заменить на описание действия. Нумерация шагов на диаграмме
компонентов не нужна: она относится к динамической диаграмме ЛР № 4, где у процесса сквозные номера
с 1 по 30, и две разные нумерации на одну систему путают при защите.

Описания четырёх связей наружу взять дословно из общей диаграммы контейнеров:

| От | К | Описание | Протокол |
|---|---|---|---|
| `lw_task_consumer` | `message_broker` | Забирает задачи разметки из очереди reviews.labeling | AMQP |
| `lw_labeling_writer` | `database` | Сохраняет результаты разметки | SQL / TCP |
| `lw_case_rule_engine` | `database` | Заводит обращение при негативе по значимой теме | SQL / TCP |
| `lw_case_rule_engine` | `message_broker` | Публикует событие «обращение создано» в очередь cases.events | AMQP |

Для связи `lw_review_loader` → `database` (чтение текста отзыва и справочника тем) в общей
диаграмме отдельной строки нет, протокол тот же — `SQL / TCP`. Описание сформулировать самому,
например «Получает текст отзыва и справочник тем». Тимлид добавит эту связь в общую диаграмму.

Внутренние связи описать действием: что один компонент передаёт другому. Например,
`lw_text_preprocessor` → `lw_bert_inference`: «Передаёт подготовленный батч токенов».

### 3.6 Подтверждение задачи брокеру

Сейчас последняя связь — `lw_case_rule_engine` → `lw_task_consumer` с подписью «ack». Это
внутренний вызов, и он правильный, но на диаграмме не видно самого подтверждения брокеру, хотя в
глоссарии у приёмника задач записано «Забирает задачи и подтверждает брокеру». Добавить вторую
связь к брокеру, по правилу «одна стрелка — одно действие»:

```text
Rel(lw_task_consumer, message_broker, "Подтверждает задачу после записи разметки в базу данных", "AMQP")
```

## 6. Что делает тимлид, а не ML

Эти пункты в зону ответственности ML не входят, новые идентификаторы в глоссарий добавляет только
тимлид. Здесь они записаны, чтобы ML о них знал и не правил глоссарий сам.

- В глоссарии нет строк для классов уровня L4 воркера разметки: контекста `ClusterAssigner`,
  интерфейса стратегии `ClusterAssignmentStrategy` и трёх её реализаций (`CosineCentroidStrategy`,
  `KnnVotingStrategy`, `FaissCentroidStrategy`). У брокера и воркера фоновых задач такие строки
  есть, у воркера разметки — нет.
- Строка `lw_strategy_factory` («Фабрика стратегий», статус «план») описывает класс, который в коде
  уже есть и называется `StrategyRegistry` (`src/individual/MLCode/cluster_assigner/registry.py`).
  Нужно согласовать имя и поменять статус на «готово».
- В общей диаграмме контейнеров нет связи «воркер разметки получает текст отзыва и справочник тем»
  (см. 3.5), хотя на L3 и на динамической диаграмме она есть.
- В `ml_context_l1.puml` и `ml_containers_l2.puml` остался внешний сервис языковой модели
  `llm_service`, которого нет в общих диаграммах: в ЛР № 2 команда перешла на собственную модель
  BERT внутри воркера. Это наследие ЛР № 1, сданной с прежним решением. Задним числом файлы
  менять не нужно; в диаграммах ЛР № 4 сервиса языковой модели нет, и на защите расхождение
  объясняется сменой решения между работами.
