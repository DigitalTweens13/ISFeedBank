# Верификационные инструкции для отчётов ЛР № 4

Папка нужна, чтобы участник мог загрузить в нейросеть свои диаграммы вместе с этими материалами и получить отчёт,
согласованный с общей системой. Нейросеть пишет текст, команда проверяет факты по чек-листу.

Файлы с суффиксом `_verification` — инструкции для отчётов ЛР № 4. Файлы с суффиксом `_fix` — разовые задания на
правку уже существующих файлов, их тоже можно отдать нейросети целиком.

| Файл | Для кого |
|---|---|
| `ML_ml_verification.md` | воркер разметки (Ершов Д. К.) |
| `BE_be_verification.md` | Backend API (Даев М. А.) |
| `BG_bg_verification.md` | воркер фоновых задач (Еловиков А. А.) |
| `DQ_dq_verification.md` | брокер сообщений (Зацепина В. В.) |
| `FE_fe_verification.md` | веб-панель и мобильное приложение (Кульбякина И. В.) |
| `ML_ml_glossary_fix.md` | воркер разметки (Ершов Д. К.): правка идентификаторов в `ml_l3.puml` под глоссарий |

Роли DA (Малахова К. В.: база данных и кэш, а также компоненты веб-панели в ЛР № 2) отдельной инструкции нет: для веб-панели используйте инструкцию FE (раздел 8), диаграммы для базы данных и кэша можно получить тем же способом из общих файлов.

## Как работать

1. Откройте файл своей роли, загрузите в нейросеть все перечисленные в разделе 1 файлы и свои PNG.
2. Вставьте шаблон запроса (ниже), подставив своё имя и роль.
3. Сверьте ответ с таблицами «Эталон» и чек-листом из своего файла. Любая правка идёт в текст отчёта; диаграммы меняет только тимлид.
4. Если эталон противоречит вашей диаграмме, не подгоняйте текст: напишите тимлиду, он поправит общую схему и перегенерирует файлы.

## Общие правила (из README репозитория и методички)

- Связи только макросом `Rel(от, кому, "описание", "протокол")`; `Rel_D`, `Rel_R`, `Rel_L`, `Rel_U`, `BiRel` запрещены.
- У каждой связи есть описание действия и технический протокол; одна стрелка — одно действие; стрелка идёт от инициатора соединения.
- Цвета, `skinparam`, `LAYOUT_WITH_LEGEND()` есть только в общих файлах тимлида (`src/landscape_l0.puml`, `src/deployment_l2.puml`, `src/dynamic_process.puml`).
- На L2 порты не указываются; они появляются только на диаграмме развёртывания.
- ID берутся из `docs/glossary/components.csv`; новые добавляет только тимлид. Для развёртывания тимлид добавил узлы `dn_*` и контейнер `database_replica`.
- Личная диаграмма — выжимка из общей: каждая связь есть в общей с тем же протоколом, нумерация шагов динамики сквозная.
- Рисунки в отчёте — экспорт из PlantUML; код в приложении совпадает с файлом.

## Как устроены личные версии

| Диаграмма | Что делается с общей |
|---|---|
| L0 | Система из чёрного ящика раскрывается в границу с контейнерами роли и их соседями; показаны только связи этого окружения, внешние системы и персоны, достижимые из него |
| Развёртывание | Остаются узлы, где живут контейнеры роли и соседи, и связи между ними; порты и шифрование те же |
| Динамика | Вырезаются шаги общего процесса, где участвует контейнер роли; номера сохраняются |

## Шаблон запроса нейросети

```text
Ты помогаешь студенту оформить отчёт по лабораторной работе № 4 (C4 Model: системный ландшафт L0, динамическая
диаграмма, диаграмма развёртывания) для «ИС управления обратной связью клиентов банка», группа ИДБ-23-13,
МГТУ «СТАНКИН». Студент: <ФИО>. Зона ответственности: <контейнер>.

Я приложил: свои три .puml и PNG, общие диаграммы, глоссарий, контракты и верификационную инструкцию.

Правила:
1. Используй только факты из приложенных файлов. Ничего не придумывай: порты, протоколы, ID, номера шагов,
   технологии и названия очередей бери из таблиц «Эталон» и из .puml.
2. Структура отчёта — раздел 2 верификационной инструкции. Стиль — как в приложенном образце (ЛР № 1–3).
3. Каждую таблицу строй из .puml без пропусков и добавлений; числа в тексте должны совпадать с диаграммами.
4. Не добавляй внешние системы, которых нет на диаграммах (в том числе сервис языковой модели).
5. В конце выведи список мест, где ты не был уверен или заметил расхождение между файлами. Не исправляй их молча.

Верни отчёт целиком, затем отдельным списком — найденные расхождения.
```
